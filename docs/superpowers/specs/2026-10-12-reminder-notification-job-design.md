# Phase 7, Spec 3 — Notification-Creation Job

**Status:** approved, ready for implementation plan
**Date:** 2026-10-12
**Scope:** A scheduled background job that turns Spec 2's due-item evaluation (`getDueBillOccurrences`, `getDueSettlements`) into real `notifications` rows, fanned out to household members per their `notification_preferences`. In-app only — email/web-push dispatch is later specs. No migration: `notifications`, `notification_deliveries`, `notification_preferences`, `push_subscriptions` all already exist from the Phase 1 schema, unused until now.

## Context

Spec 1 shipped the BullMQ/Redis queue (`Queue`/`FakeQueue`/`BullMQQueue`, `worker.ts`, the `heartbeat` job as a working proof). Spec 2 shipped `reminder_rules` CRUD and the pure evaluation functions `getDueBillOccurrences`/`getDueSettlements` (in `reminder-evaluation.service.ts`), each returning due items with `daysUntilDue`, `matchedOffsets` (the subset of the rule's `offsetsDays` equal to `daysUntilDue`), and `isOverdue` (folds in the rule's `overdueDaily` flag). Neither evaluation function currently returns the rule itself — only the computed outcome — so this job needs the effective rule's `sendHour` too; `reminder-evaluation.service.ts` will export the rule alongside each due item (or a parallel lookup) rather than duplicating `loadRules`/`effectiveRule`.

The `notifications` table's own doc comment already specifies the idempotency key shape: `"bill_occ:<id>:before:3:user:<id>"`. `EmailProvider` (`ConsoleEmailProvider`/`MemoryEmailProvider`) and `Deps.email` already exist (added ahead of schedule) but are out of scope here — this job writes `PENDING` `notification_deliveries` rows for non-IN_APP channels for a later dispatcher to pick up; it never calls `deps.email.send`.

## Job

- **New file** `apps/api/src/jobs/evaluate-reminders.job.ts`, exporting `runEvaluateReminders(deps: Deps): Promise<void>`, registered in `worker.ts` as `deps.queue.registerHandler("evaluate-reminders", () => runEvaluateReminders(deps))` and scheduled via `deps.queue.scheduleRepeating("evaluate-reminders", {}, 60 * 60 * 1000)` (hourly — mirrors the heartbeat's `scheduleRepeating` call, just a longer interval).
- **Household loop:** select all non-archived `households` (`archivedAt IS NULL`). For each, compute `today = dateInZone(deps.clock.now(), household.timezone)` and `hour = hourInZone(deps.clock.now(), household.timezone)`, then call `getDueBillOccurrences(deps, household.id, today)` and `getDueSettlements(deps, household.id, today)`.
- **Per-item gating:** a due item is actionable this tick only if (a) it has a non-empty `matchedOffsets` or `isOverdue`, AND (b) its effective rule's `sendHour === hour`. An item can match both an offset and be overdue only in theory (an occurrence can't be both since `isOverdue` requires `daysUntilDue < 0` and a matched offset requires `daysUntilDue === offset >= 0` — mutually exclusive), so each actionable item produces exactly one outcome: `"before"` (with the matched offset) or `"overdue"`.
- **Recipient fan-out:** for each actionable item, select all `household_members` rows with `status = 'ACTIVE'` for that household. For each member, look up their `notification_preferences` row for `(householdId, userId, category)` where `category` is `BILL` or `SALARY` matching the item type. No row = treated as enabled (matches the column's own `enabled.default(true)`) with default channels `{IN_APP, WEB_PUSH}`. A row with `enabled = false` skips that user entirely for this item.
- **Idempotency key:**
  - Offset match: `` `bill_occ:${occurrenceId}:before:${offset}:user:${userId}` `` / `` `settlement:${settlementId}:before:${offset}:user:${userId}` ``
  - Overdue (must re-fire daily while unpaid, since the underlying condition persists): `` `bill_occ:${occurrenceId}:overdue:${today}:user:${userId}` `` / `` `settlement:${settlementId}:overdue:${today}:user:${userId}` ``
- **Insert:** one `notifications` row per (item, user) with `category` (`BILL`/`SALARY`), `severity` (`URGENT` if overdue, `WARNING` if `offset <= 1`, else `INFO`), `title`/`body` built from a small per-category/outcome template (e.g. `"${billName} due in ${offset} day(s)"`, `"${billName} overdue by ${-daysUntilDue} day(s)"`), `entityType`/`entityId` pointing at the occurrence/settlement row, `data` carrying `{amountDuePaise | netPayablePaise, dueDate}`. A unique-violation on `notifications_idempotency_uq` (re-run of the same hour, or a retried job) is caught and treated as "already created," not an error.
- **Deliveries:** for each enabled channel on that user's effective preference (`IN_APP` always counts as enabled even with no preference row), insert a `notification_deliveries` row (`status: "SENT", sentAt: now` for `IN_APP`; `status: "PENDING"` for any other channel) — skipped entirely if the parent `notifications` insert was a duplicate (no new delivery rows for an item/user that already has a notification).
- Wrap each item's (notification + its deliveries) insert in one transaction so a partial failure can't leave a notification without any delivery rows.

## Testing

- **API integration** (`evaluate-reminders.job.test.ts`, real test DB, `FakeQueue.runHandler`, a fixed `Clock`): a due bill occurrence at a matched offset creates one `notifications` row per active member with that preference enabled; re-running the same tick creates no duplicates; a member with `notification_preferences.enabled = false` for `BILL` gets nothing; an overdue occurrence creates a notification today and a second one tomorrow (different idempotency key) but not twice today; `sendHour` gating — an item whose rule's `sendHour` doesn't match the household's current local hour produces nothing; cross-household isolation (household B's due items never produce household A's notifications); a member with no `notification_preferences` row still gets an `IN_APP` notification (default-enabled behavior).
- No web UI in this spec (nothing to display notifications yet — that's Spec 4).
