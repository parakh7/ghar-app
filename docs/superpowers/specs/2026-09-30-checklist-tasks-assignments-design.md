# Phase 4, Spec 1 — Checklist Tasks and Assignments

**Status:** approved, ready for implementation plan
**Date:** 2026-09-30
**Scope:** Full CRUD for checklist tasks (with frequency config, priority, reordering, archiving) and versioned assignment of tasks to one or more househelps. Sets up the data daily completion marking (Spec 2) will consume. No migration — `checklist_tasks`, `checklist_assignments` already exist from Phase 1.

## Context

Phase 1 already delivered the schema: `checklist_tasks` (name, description, optional `categoryId` FK into the existing `househelp_categories` table — so checklist tasks can be tagged with the same categories used for househelps, e.g. "Cleaning" — `frequency` enum `DAILY|WEEKLY|WEEKDAYS|MONTHLY|SPECIFIC_DATE|CUSTOM` with the frequency-specific columns already present: `weekdays` (WEEKLY/WEEKDAYS), `dayOfMonth` (MONTHLY), `specificDate` (SPECIFIC_DATE), `intervalDays`+`anchorDate` (CUSTOM); `priority` enum `LOW|NORMAL|HIGH` default `NORMAL`; `sortOrder`; `isActive`; `archivedAt` soft-delete), `checklist_assignments` (versioned, `effectiveFrom`/`effectiveTo`, one row per (task, househelp) assignment period — a task can have zero, one, or several currently-assigned househelps at once), and `checklist_completions` (Spec 2's table, untouched here). Permissions `checklists.view`, `checklists.manage`, `checklists.complete` already exist with correct default grants (OWNER/ADMIN manage, MEMBER view+complete, VIEWER view). No new permissions, no migration.

## Tasks

- **API:** `GET /checklist-tasks` (`?includeArchived=true`, default excludes archived), `POST /checklist-tasks`, `GET /checklist-tasks/:id`, `PATCH /checklist-tasks/:id` (any subset of fields), `POST /checklist-tasks/:id/archive`, `POST /checklist-tasks/:id/unarchive`, `POST /checklist-tasks/:id/move` (`{direction: "up"|"down"}`, reorders within the household by `sortOrder`, same swap-by-index pattern as category reordering). All require `checklists.view`/`checklists.manage` as appropriate.
- **Frequency validation.** Each `frequency` value requires exactly its own config fields and rejects the others: `DAILY` takes none; `WEEKLY`/`WEEKDAYS` require `weekdays` (WEEKDAYS is a fixed Mon–Fri set — reject a client-supplied `weekdays` for it, storing the canonical `[1,2,3,4,5]` instead — WEEKLY's `weekdays` is free-form 1–7); `MONTHLY` requires `dayOfMonth` (1–31, clamped to the actual month's last day at completion-check time in Spec 2, not stored clamped); `SPECIFIC_DATE` requires `specificDate`; `CUSTOM` requires `intervalDays` (≥1) and `anchorDate`. This mirrors how `salaryMode` doesn't gate which salary fields are *stored* (Phase 2's precedent) — but frequency config is different: an inapplicable field left populated would make Spec 2's "is this due today" logic ambiguous, so the schema validates that only the relevant fields are provided for the given `frequency` (zod's `.superRefine`), unlike the salary fields' looser stance.
- **Category tagging.** `categoryId` is a single optional FK (not a many-to-many like househelps' `categoryIds`) — a checklist task belongs to at most one category. Reuses the same active-categories list already built for househelps; no new category CRUD.
- **Reordering, archiving, audit logging, cross-household isolation** all follow the exact conventions established in Phase 2 (index-adjacency reorder inside a transaction with a row lock; `archivedAt` one-way-by-default with an `unarchive` recovery action; `recordAudit` inside the same transaction as every mutation; `requireHousehold` + `req.membership.householdId`, never the raw URL param).

## Assignments

- **API:** `GET /checklist-tasks/:id/assignments` (returns the currently-effective assignee `househelpId`s, `checklists.view`), `PUT /checklist-tasks/:id/assignments` `{househelpIds: string[]}` (fully replaces the currently-effective set, `checklists.manage`).
- **Versioning, simplified from the single-assignee schedule pattern.** Because a task's assignee set can have zero-to-many currently-effective members (not the schedule's always-exactly-one-currently-effective-row), `PUT` does not attempt the schedule's same-day-edit-updates-in-place optimization: inside one transaction, currently-effective rows (`effectiveFrom <= today`, `effectiveTo` null or `>= today`) whose `househelpId` is no longer in the new set get `effectiveTo = yesterday`; `househelpId`s in the new set that aren't already currently-effective get a fresh row with `effectiveFrom = today`; `househelpId`s already currently-effective and still in the new set are untouched. A household re-assigning the same task twice in one day creates a closed-then-reopened row pair instead of updating in place — a minor, accepted history-noise tradeoff (not a correctness issue) rather than replicating schedule's more intricate single-row special case for a fundamentally different (set-valued) shape.
- Every `househelpId` in the input must belong to the same household (validated the same way category/househelp IDs are validated elsewhere) — an unknown or cross-household ID is a 400, not a silent no-op.

## Web UI

- A checklist list page (grouped by category, mirroring `HousehelpsListPage`'s existing grouping pattern, with an "Uncategorized" bucket) replacing the `/checklist` route's `ComingSoonPage`, showing each task's name, frequency (human-readable, e.g. "Every Mon, Wed, Fri", "Monthly on the 15th"), priority badge, and currently-assigned househelp name(s).
- A create/edit form: name/description, category picker (reusing the existing category-picker UI piece), frequency picker (a type selector that reveals only the relevant config inputs per type — weekday chips reusing the existing `.chip[aria-pressed]` weekday-picker piece for WEEKLY, a day-of-month number input for MONTHLY, a date input for SPECIFIC_DATE, an interval-days number input + anchor date for CUSTOM), priority selector, archive/unarchive action.
- An assignment editor on the task detail page: a multi-select list of the household's active househelps (checkbox-style, reusing `.chip[aria-pressed]` again) reflecting the currently-effective set, saved via the `PUT` endpoint.

## Testing

- **API integration:** task CRUD, frequency-config validation (each frequency rejects the others' fields, accepts only its own), reorder correctness, archive/unarchive round-trip, category-tag validity (rejects a category from another household), permission checks (VIEWER/MEMBER blocked from manage routes); assignment GET-with-none-yet, PUT establishing the first assignee set, PUT adding/removing assignees (closes removed, opens added, leaves unchanged ones alone), PUT rejecting a househelp ID from another household, household-timezone-correct today/yesterday boundary (same `FakeClock` pattern as the schedule-versioning tests).
- **Web:** component tests for the list page (grouping, permission-gated actions), the create/edit form (frequency-type switching reveals/hides the right fields, validation), and the assignment editor (checkbox state reflects current assignees, PUT body shape on save).
- **E2E:** not added, consistent with prior specs' scope decisions.
