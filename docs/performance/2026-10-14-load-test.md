# Load & Performance Test Results — 2026-10-14

Phase 10, Spec 3 (final spec of the 10-phase roadmap). See
`docs/superpowers/specs/2026-10-14-load-perf-testing-design.md` for the approved design.

## Setup

- Dedicated throwaway database `household_loadtest`, created, migrated, and seeded fresh for this
  run, dropped afterward. Never touched `household_dev`/`household_test`.
- Seed: one household ("Shah Family"), one login user, 3 househelps, 3 daily checklist tasks —
  created via the real running API (the base `db:seed` script only creates users/household/members).
- Real API server, started via `tsx src/server.ts` directly (not watch mode), pointed at
  `household_loadtest`.
- `autocannon` (v8.0.0, via `npx`) as the load generator, run from the same machine as the server
  (see Caveats).
- `RATE_LIMIT_GLOBAL_MAX` and `RATE_LIMIT_AUTH_MAX` were raised for the duration of this test only.
  At their normal defaults (300/min global, 10/15min auth), both limiters are IP-keyed and trip
  almost immediately under a 50-connection sustained load from a single IP — that's the rate
  limiter working as designed (verified in the security review), not an app bottleneck, so it was
  excluded from these measurements to see the underlying endpoint cost.

Each scenario: 50 concurrent connections, 30 seconds.

## Results

### 1. Read-heavy

| Endpoint | p50 | p95 | p99 | Req/sec (avg) | Errors |
|---|---|---|---|---|---|
| `GET /today` | 171 ms | 556 ms | 1052 ms | 232 | 0 (6,963 × 200) |
| `GET /search?q=load` | 168 ms | 516 ms | 649 ms | 252 | 0 (7,549 × 200) |

Threshold (p95 < 200ms, zero errors): **zero errors met; p95 latency missed** on both endpoints.

### 2. Write-heavy

| Endpoint | p50 | p95 | p99 | Req/sec (avg) | Errors |
|---|---|---|---|---|---|
| `PUT /attendance/:id` | 141 ms | 455 ms | 623 ms | 290 | 0 (8,696 × 200) |
| `PUT /checklist/:id/completion` | 128 ms | 367 ms | 477 ms | 324 | 0 (9,711 × 200) |

Threshold (p95 < 200ms, zero errors): **zero errors met; p95 latency missed** on both endpoints.

### 3. Auth

| Endpoint | p50 | p95 | p99 | Req/sec (avg) | Errors |
|---|---|---|---|---|---|
| `POST /auth/login` | 667 ms | 1340 ms | 1391 ms | 68 | 0 (2,050 × 200) |

No pre-set threshold (argon2id is deliberately CPU-expensive — m=19MiB, t=2, p=1, documented in
the README). Latency is high but stable (max 1724ms, not far above p99, and stdev is a modest
218ms) — no sign of unbounded growth over the 30s run. This is 50 concurrent password hashes
competing for CPU on an 8-core box; expected behavior for this primitive, not a defect.

## Bottleneck found and fixed

`GET /today` originally awaited its four independent sections (attendance, checklist, bills,
salary) **sequentially** in `today.service.ts`, each its own DB round-trip, instead of
concurrently. Fixed by switching to `Promise.all`. Verified via `tests/today.test.ts` (10/10
still passing).

Also made the Postgres pool size configurable (`DATABASE_POOL_MAX`, default raised 10 → 20) in
`db/client.ts`/`config/env.ts`, applied to both `server.ts` and `worker.ts` — the old hardcoded
10-connection cap had no way to tune it per deployment. This did not move the measured numbers in
this environment (see Caveats) but is a correct, low-risk change on its own merits: a single
API instance with no override previously could never use more than 10 concurrent DB connections
regardless of available Postgres capacity.

## Caveats

- **Client and server share one 8-core machine.** `autocannon`, the Node API process, and the
  Postgres/Redis Docker containers all compete for the same CPU during these runs. That inflates
  and adds variance to every latency number above — re-running the `/today` fix showed *better*
  median latency (171ms vs 217–241ms before) but a *noisier* tail (p95 556ms vs 352–489ms before),
  which is consistent with CPU contention noise rather than the fix making things worse. These
  numbers are useful for spotting relative bottlenecks (sequential vs. parallel, which endpoint is
  slower) but should not be read as true network-separated production latency.
- The dataset is intentionally tiny (3 househelps, 3 tasks) — these results say nothing about
  query behavior at production-scale row counts. No index or query-plan issues were visible at
  this scale; that question is out of scope for this measurement.
- Given the caveat above, the p95<200ms threshold miss on every read/write endpoint is **not**
  treated as a go/no-go failure — it's reported honestly, with the parallelization fix applied as
  the one fix clearly justified independent of the measurement noise. A cleaner measurement would
  need a separate load-generation host, which is out of scope for this sandbox.

## Out of scope (per spec)

- BullMQ job-processing throughput (reminder/notification jobs) — a different kind of load test.
- Web frontend bundle/render performance.
